# Скорость Game Boy

**Текущий режим восстановления:** после сообщения пользователя о неработающем
Game Boy прошивка возвращена к обычной SPI-передаче на 10 МГц без DMA.
Тройная буферизация, масштабирование полосами и поиск изменившихся областей
сохранены. DMA включается только явно через `-DROBOT_GB_DMA=1`; профиль
`robot-fast` с 40 МГц также экспериментальный. Приведённые ниже быстрые замеры —
история проверки исполнения и передачи, а не подтверждение работоспособности
изображения на физической панели. Снимки `v` считывают программный буфер.

## Причина низкого FPS

Измерение на AI-S3 N16R8, ST7789 320×240, SPI 10 МГц, собственный
`openplay-test.gb`, около 10 секунд на каждый замер:

| Сцена | Эмуляция, кадров/с | Обновления LCD, кадров/с |
| --- | ---: | ---: |
| Полная прокрутка, прежний вывод | 59,76 | 7,71 |
| Полная прокрутка, новый вывод, 10 МГц | 59,73 | 9,54 |
| Движущийся участок 8×8, новый вывод, 10 МГц | 59,73 | 59,73 |
| Полная прокрутка, новый вывод, 40 МГц | 59,73 | 36,47 |

Прежний код разрешал передачу только каждого третьего эмулированного кадра.
Общий mutex удерживался на протяжении масштабирования и всей передачи SPI.
Пока он был занят, эмулятор отбрасывал новые кадры без сохранения последнего.
Экран дополнительно ждал следующего разрешённого кадра после завершения передачи.
Изображение целиком масштабировалось в PSRAM и отправлялось даже при изменении
одного небольшого объекта.

Сам эмулятор в этом тесте уже работал с нормальной скоростью Game Boy. Основная
проблема была в выводе изображения. Для тяжёлого ROM это надо проверять отдельно:
низкий `emu_fps` означает, что ограничением стала эмуляция, а не только LCD.

## Новый вывод

- Три исходных буфера 160×144, по одному байту на оттенок. Эмулятор пишет в свой
  буфер, renderer читает свой, третий хранит последний готовый кадр. Подмена
  указателей защищена короткой критической секцией, без ожидания SPI.
- Ожидающий кадр заменяется новым, если экран ещё занят. Очередь не растёт;
  после передачи берётся самое свежее изображение. Никакого фиксированного
  пропуска двух кадров из трёх больше нет.
- После смены буфера копируется исходное изображение 23 040 байт. Это сохраняет
  строки, которые эмулятор может не выдать, например при выключенном GB LCD.
- Изменения ищутся блоками 8×8 относительно **последнего полностью переданного**
  изображения. Соседние блоки объединяются в прямоугольники. До 32 областей;
  более дробные изменения отправляются одним полным кадром. Неизменившийся
  кадр вообще не требует SPI-передачи.
- Масштабирование идёт сразу в небольшие буферы внутренней RAM,
  по 266×8 RGB565, с заранее рассчитанными координатами. Обычный вывод использует
  `pushImage` и `setSwapBytes(true)`, как до ускорения; экспериментальный DMA
  получает пиксели сразу в порядке байтов провода. Полный увеличенный буфер
  размером 127 680 байт в PSRAM больше не нужен. Перекрытие передачи одной
  полосы заполнением другой используется только при явно включённом DMA.
- Renderer остаётся на ядре 0; эмуляция и кнопки — на ядре 1. Системная пауза
  дожидается завершения передачи, очищает ожидающий кадр и затем отдаёт экран меню.
  Продолжение принудительно перерисовывает весь экран после очистки меню.
- Wi-Fi при запуске GB приостанавливается, при выходе восстанавливается.
  Сохранённые настройки не меняются. STA и AP используют ограничение мощности
  8,5 dBm для USB-питания макетки.
  Ограничение применяется напрямую через ESP-IDF перед подключением: Arduino
  `setTxPower` сразу после `mode` может отвергнуть вызов, пока не обработано
  асинхронное событие `STA_STARTED`.

Масштаб остался прежним: 266×240, весь исходный кадр 160×144 без обрезки,
поля по 27 пикселей. Снимок `v` строится из последнего переданного исходного
кадра с тем же масштабированием и палитрой, а не из следующего ожидающего.

## Предел SPI и быстрый профиль

Один полный кадр: `266 × 240 × 2 = 127 680` байт.
На SPI 10 МГц только передача данных занимает минимум **102,144 мс**:
теоретический предел около **9,79 полных кадров/с**, ещё без команд и обработки.
Буферизация устраняет лишние паузы, но не увеличивает пропускную способность
провода. Обновление небольших областей позволяет показывать движение с 60 FPS
на этой же частоте; постоянная прокрутка всего экрана требует большей частоты.

Окружение `robot-eyes` использует **10 МГц без DMA**.
Экспериментальное окружение `robot-fast` использует **40 МГц**, также без DMA
по умолчанию; теоретический предел полного
кадра около **39,16 FPS**. Для него нужны надёжные контакты и короткие SPI-провода.
На подключённой плате с новым выводом измерено **36,47 FPS** полной прокрутки —
примерно в **4,7 раза** больше исходных 7,71. Изменения небольшого участка
проверены отдельно на 10 МГц. Это результаты собственных тестовых ROM,
а не гарантия такой скорости для каждой коммерческой игры.

```powershell
# Экспериментальный быстрый профиль, не рекомендуется без проверки панели
.\tools\pio.ps1 run --environment robot-fast --target upload --upload-port COM6

# Консервативный профиль, если на физическом экране появились помехи
.\tools\pio.ps1 run --environment robot-eyes --target upload --upload-port COM6
```

Частота задаётся `ROBOT_DISPLAY_SPI_HZ`; диагностические окружения с
`ROBOT_DISPLAY_SLOW_SPI` сохраняют приоритет своей частоты 1 МГц.
Снимок буфера подтверждает геометрию и алгоритм масштабирования, но не качество
физического сигнала SPI и цветопередачу панели.

## Как повторить измерение

```powershell
python tools/make_gb_test_rom.py .pio/inspection/openplay-test.gb
python tools/make_gb_test_rom.py .pio/inspection/openplay-tile.gb --scene tile
```

Первый ROM прокручивает весь экран. Второй двигает маленький узор на однотонном
фоне. Оба — собственные тестовые программы проекта, с сохранением счётчика запусков.
Загрузи ROM через обычный раздел Game Boy, запусти нужную игру и закрой меню паузы.

```powershell
python tools/measure_gb.py --port COM6 --seconds 10 --output .pio/gb-fps.json
```

Нужен pyserial; если он установлен только в окружении PlatformIO, используй его
Python. Утилита отправляет только `s`; она не запускает и не закрывает игры и не
меняет настройки. Не снимай скриншот и не открывай паузу во время измерения.
Для честного сравнения используй один ROM, одну сцену и одну частоту SPI.

Новые поля `GAMEBOY_VIDEO` в Serial Monitor:

| Поле | Значение |
| --- | --- |
| `displayed` | Число кадров с фактической передачей изменившихся пикселей |
| `consumed` | Обработанные renderer кадры, включая полностью неизменившиеся |
| `replaced` | Заменённые более свежим изображением ожидающие кадры |
| `dma`, `spi_hz` | Используется ли DMA и частота SPI |
| `emu_fps`, `lcd_fps` | Частота эмуляции и фактических LCD-обновлений между запросами `s` |
| `emu_us` | Среднее время выполнения `gb_run_frame`, мкс |
| `render_us` | Среднее время обработки кадра renderer, включая DMA, мкс |
| `spi_us` | Среднее время в вызовах передачи/ожидания SPI; заполнение второго буфера частично перекрывает DMA |
| `bytes`, `rects` | Суммарно переданные байты RGB565 и прямоугольники |

В полностью статичной сцене `lcd_fps=0` — нормальный результат: перерисовка
одинаковой картинки не нужна. Смотри также `emu_fps` и `consumed`. Счётчики времени
эмуляции/вывода усредняются за запуск; FPS считается с предыдущего `s` или
продолжения игры, поэтому не включай паузу в интервал замера.

## Проверки алгоритма

```powershell
python tools/check_gb_video.py
.\tools\pio.ps1 run
```

Native-тест требует clang++. Он использует производственные `Mailbox`,
`findDamage` и `Scaler` из `include/gb_video.h`: проверяет неподвижность буфера
занятого renderer, выбор последнего кадра, очистку очереди при паузе, неизменившиеся
кадры, границы DMA-полос, RGB565 и точное совпадение частичных обновлений с полной
отрисовкой. Проверено 250 последовательных локальных изменений, в среднем
1209 байт на обновление вместо 127 680 байт полного кадра.

DMA-ограничения проверены по закреплённому
[исходнику TFT_eSPI 2.5.43 для ESP32-S3](https://github.com/Bodmer/TFT_eSPI/blob/V2.5.43/Processors/TFT_eSPI_ESP32_S3.c):
полосы находятся во внутренней DMA RAM и существенно меньше лимита передачи;
перед повторным использованием буфера и передачей экрана оболочке вызывается
`dmaWait`. Принципы владения буферами описаны также в
[документации SPI ESP-IDF 4.4.7](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/peripherals/spi_master.html).

Проверка исполнения предыдущей прошивки `robot-fast` включала запуск без
перезапусков при подключённом Wi-Fi, счётчики DMA-передач, сохранение и выход,
возврат к глазкам и восстановление подключения к домашней сети. Однако она
не подтвердила изображение на физической панели. После сообщения пользователя
о неработающем Game Boy этот режим отключён в обычной прошивке.

В режиме восстановления `robot-eyes` на плате проверен запуск
`super_mario_land_world.gb` с `dma=0 spi_hz=10000000`, выполнение кадров,
пауза, отправка START через меню паузы и продолжение без ошибок. При обычной
передаче используются исходные RGB565-цвета и штатная перестановка байтов
TFT_eSPI, как в прежнем выводе. Изображение на самой панели остаётся предметом
проверки пользователем; выполнение эмулятора не выдаётся за такую проверку.
